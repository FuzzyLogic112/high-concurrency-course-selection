# 设计说明与踩坑记录

README 讲的是"做了什么"，这里讲"为什么这么做"，以及过程中走错的路。

---

## 为什么名额的真相源是 Redis 而不是数据库

一种常见做法是反过来：以数据库为准，用 Canal 之类的工具把变更同步回缓存。这条路在选课场景下有问题——缓存更新滞后期间，学生读到的是旧余量，照样会超选。

本项目把 Redis 作为名额的**唯一真相源**：预扣在 Redis 完成，数据库只负责最终落账。代价是 Redis 一旦挂掉，已预扣未落库的名额会丢失。这个不足是已知的，对账任务能事后检出偏差，但没有自动恢复能力。改进方向是引入持久化或主从切换。

## 为什么不用分布式锁

分布式锁本质还是**加锁串行化**：请求排队等锁，还要处理锁超时、锁续期、误删别人的锁。Lua 是把多条命令**合并成一次原子执行**，Redis 执行脚本期间不处理其他命令，根本不存在锁竞争，也不需要重试。

前提是脚本必须简短、不含耗时循环，否则会阻塞整个 Redis 实例。本项目的扣减脚本十余行、无循环。

## 判重为什么必须写在脚本里

如果把 `SISMEMBER` 判重放到脚本外面，就是两次独立的网络往返。同一个学生的两个并发请求会双双通过判重，然后各扣一个名额。

判重必须和扣减在同一个原子区间里才有意义——这跟名额扣减本身要原子，是同一类问题。

## 乐观锁的重试循环为什么在事务外

最初把重试循环写在事务方法里，结果**重试全部失败**。

原因是可重复读隔离级别下，事务内多次读取看到的是同一份快照，版本号在事务内永远不变。每次重试读到的都是同一个已失效的版本号，CAS 必然失败。

改法是把单次 CAS 和重试循环拆开：单次尝试各自开独立事务，循环在事务外控制。

```java
for (int i = 0; i < MAX_RETRY; i++) {
    DeductOutcome r = writer.casOnce(classId, studentId, roundId);  // 独立事务
    if (r != DeductOutcome.RETRY) return r;
}
```

## 唯一约束会挡住合法的重复操作

选课记录表上 `(学生号, 教学班号)` 的唯一索引是消费端幂等的最后一道防线。但它同时带来一个后果：**学生退选之后无法重新选回这门课**。

链条有三层：

1. 退选是软删除，状态置为已退选、行保留。而重复选课校验最初直接查记录是否存在，没区分状态，于是退过一次就被永久判成"已选过"。
2. 即便放行了校验，`course_selection` 的唯一索引会拒绝重新插入。
3. 本地消息表的 `biz_key` 是"学生号:教学班号"，同样有唯一约束，新消息也写不进去。

修法是不动唯一约束——去掉它等于把幂等保证拆了。改成：校验只统计处于已选状态的记录；写入撞上唯一键冲突时，再用**一条带状态条件的 UPDATE** 尝试把已退选的记录复活：

```sql
UPDATE course_selection SET status = 1, round_id = ?, updated_at = ?
WHERE student_id = ? AND teaching_class_id = ? AND status = 2
```

受影响行数为 1 说明是重选，为 0 说明那行本来就是已选（即重复消息）。判断与写入合并在同一条语句里，中间没有并发窗口——和扣减问题的解法是同一个思路。

这个缺陷一直没被发现，是因为功能测试里有「退课归还余量」，却没有「退选之后再选一次」。**测了每一步，没测两步的组合。**

## 压测端为什么自己写

一开始用 Python 脚本压测，结果 500 并发时四种方案的 QPS 全挤在 90 左右。那不是服务端的能力，是**压测端自己的天花板**——四条曲线重合本身就是信号。

改用 JDK 虚拟线程重写后，同样并发能打到 1000 以上，客户端瓶颈消失。JMeter 也能做到，但要装 90MB 的包，而且图形界面本身就吃资源。

压测端见 [`verify/loadtest/LoadTest.java`](../verify/loadtest/LoadTest.java)，零第三方依赖，`javac` 一条命令编译。

## 3000 并发下几百个请求失败，不是系统扛不住

那些失败发生在**请求进入应用之前**：Tomcat 的 `accept-count` 默认只有 100，瞬时涌入的连接在操作系统 backlog 层面就被拒了。

调成 3000 之后失败数从 729 降到 38，占比 1.3%。这个现象看起来像应用性能不足，实际是容器参数没调，很容易误判。

## 位图实验为什么要专门构造"不冲突"的候选课

朴素实现**一命中冲突就提前返回**。如果候选课随机生成，已选课程越多反而越容易早退出，测出来的平均耗时几乎不增长，曲线是平的，看不出 O(n×m)。

只有构造一定不冲突的候选课、迫使它扫完全部已选课程，才能暴露真实复杂度。实验里同时记录平均与最坏耗时，就是为了说明这件事。

### 中途修掉的三个方法问题

| 现象 | 真实原因 | 处理 |
|---|---|---|
| n=14 时构造不出候选集 | 5 天 × 12 节只有 60 个槽，放不下 14 门互不冲突的课 | 上限降到 12，并改为在全部 7 天上生成 |
| n=2、4 的耗时反而比 n=6 高 | **缓存局部性**：稀疏课表要访问 64 个不同的 `long[]`，稠密课表反复命中同几个，全在 L1 里 | 改为共用一套按最大规模构造的候选集 |
| 首档耗时偏高 | CPU 睿频爬坡 | 每档跑 3 次取最小值 |

第二条是最容易漏掉的——先加了全局 JIT 预热，**没有任何效果**，才意识到问题不在编译而在内存访问模式。

## 前端：localStorage 不是响应式数据源

`App.vue` 里最初这样判断角色：

```js
const isAdmin = computed(() => localStorage.getItem('role') === '3')
```

这个 `computed` **没有任何响应式依赖**，首次求值后被永久缓存。结果是：登录成功后导航栏出现了，但"教务后台"入口不会出现，必须按 F5 整个应用重新挂载才行。看起来像偶发卡顿，其实是必现。

反向也坏：管理员退出后登学生账号，`isAdmin` 仍缓存着 `true`，学生会看到管理入口（路由守卫拦得住，但入口不该露出来）。

改法是把登录态放进 `reactive` 对象作为唯一真相源，写入时同步落 `localStorage`。现在全前端只有 [`stores/auth.js`](../frontend/src/stores/auth.js) 一个文件碰 `localStorage`。

## 垂直越权与水平越权要分开处理

- **垂直越权**（学生能不能调教师接口）：按 URL 前缀在拦截器统一校验角色。
- **水平越权**（教师甲能不能查教师乙班级的名单）：必须在接口内部逐条比对资源归属。

后者拦截器做不了，因为它不知道"这条数据属于谁"。教师端查名单时会先校验该教学班的任课教师是否为当前登录者，不匹配一律拒绝，且**不区分"班不存在"和"不是你的班"**——避免被拿来枚举教学班归属。

选课接口的学生身份一律从 JWT 里取，绝不接受前端传入的 `studentId`，否则改个请求参数就能替别人选课。

## 实验数据的可信边界

所有数据都是本机单机测的，压测端与被测服务抢同一份 CPU。因此：

- **超选与否是定性结论，与机器配置无关**，单机也成立。
- **吞吐量的绝对值偏低**，所以全程只用相对比较，从不把任何一个 QPS 数字说成系统的承载上限。

`verify/results/` 下每个 CSV 的文件头都写明了测试环境、方法与该组数据能支撑什么结论、不能支撑什么结论。其中 `api-stress.csv` 是早期 Python 压测的结果，已标注作废——留着是为了说明"客户端瓶颈"这个坑长什么样。
